# セキュアコーディングレビュー — 2026-10-27

MioNote 0.10.0のRustソース、Win32／WinRT境界、依存関係、配布処理を確認し、0.11.0で修正した。
判定はこの時点の実装・検証範囲に対するもので、特定の規格への適合認証ではない。
0.12.0の変更と追加検証は[Store／ポータブル版の追加レビュー](store-security-review-20261027.md)に記録した。依存監査JSONは現在のCargo.lockに対する最新の記録とする。
入力検証は[OWASPの指針](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html)、
DLL読み込みは[Microsoftの指針](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-security)を参照した。

## 対象と前提

対象はローカルのWindows 11 on Armアプリで、ノート・設定・保存先を入力境界とする。
共有されたノートは信頼しない。ZIPのパスをファイルシステムへ展開せず、定義済みのエントリーだけをメモリー内で扱う。
ノートにスクリプト、外部画像URL、フォント、PDFアクションを取り込む機能はない。
アプリは管理者権限を要求しない。保存先ディレクトリー自体のアクセス権はWindowsと利用者が管理する。

## 指摘と修正

重要度「中」は主にローカルデータの保全、または細工されたファイルを開いたときの可用性への影響を表す。
任意コード実行が確認されたという意味ではない。

| ID | 重要度 | 0.10.0の問題 | 0.11.0の対応と確認 |
| --- | --- | --- | --- |
| S-01 | 中 | 設定の一時ファイル名がPIDから予測でき、File::createで既存ファイルやハードリンク先を切り詰める | storage.rsへ保存処理を共通化。排他的なcreate_new、別名への置換、例外時の後始末。旧一時ファイル名のハードリンクを事前作成しても被害対象が変わらないことを確認 |
| S-02 | 中 | ZIPの件数チェックより前に中央ディレクトリーのテーブルを確保していた。余分なエントリーや二重ヘッダーの解釈も曖昧 | 件数を実際の読み込み中に制限するストリーム方式へ変更。ヘッダー整合検証を有効化し、重複・想定外の名前・壊れたCRC・不一致の件数・切り詰めを拒否 |
| S-03 | 中 | ISFの復元後に座標・行列・線幅・筆圧・点数などをアプリ側で検証していなかった。出力量にも合計上限がなかった | ワーカーで有限数・範囲・複雑度を検証。描画API直前にも座標と幅を確認し、全ページで共有する描画予算と出力バイト予算を追加。不正入力時に既存出力を保持するテストを追加 |
| S-04 | 中 | ノート保存時には拡張子を検証せず、誤って指定した別形式ファイルも上書きし得た。代替データストリームやデバイスパスも明示拒否していなかった | ダイアログと処理本体の双方で形式別の拡張子を検証。デバイス名・パイプ・ADS・末尾ドットなどを共通で拒否。exe指定時に既存内容が変わらないことを確認 |
| S-05 | 改善 | プロセス全体と静的インポートのDLL探索制限、CFGが明示されていなかった | System32に探索を制限し、CFGを有効化。ASLR・DEPと併せてPEヘッダーを確認。asInvokerのマニフェストも追加 |
| S-06 | 依存関係 | zip 2.4.2に3件のアドバイザリーが検出された | zip 9.1.2へ固定更新。依存45件をOSVへ照合し検出0件。ライセンス表記も更新 |

S-06の3件は[RUSTSEC-2026-0367](https://rustsec.org/advisories/RUSTSEC-2026-0367.html)、
[0368](https://rustsec.org/advisories/RUSTSEC-2026-0368.html)、[0369](https://rustsec.org/advisories/RUSTSEC-2026-0369.html)。
対象はZIPのディスク展開APIで、このアプリはそれらのAPIを呼んでいない。
Unixの権限処理もWindows向け実行ファイルの経路ではないため、アプリで到達可能な重大脆弱性としては扱っていない。
それでも既知の問題を持つ依存バージョンを残さない方針で更新した。
照合結果とCargo.lockのハッシュは[依存監査の記録](dependency-audit-20261027.json)に保存した。

## 入出力の上限

| 対象 | 上限・条件 |
| --- | --- |
| ノートファイル | 128 MiB、通常の.inknoteファイル |
| ページ・エントリー | 1000ページ、文書情報を含め1001エントリー。Stored方式のみ |
| 文書情報 | 1 MiB、既定の形式バージョン・用紙・向き・罫線間隔。未知フィールドも拒否 |
| ISF | 1ページ8 MiB、全体64 MiB |
| ストローク | 全体10万本 |
| 筆点・描画セグメント | それぞれ全体200万、1ストロークの筆点10万 |
| 数値 | 有限数。正規化座標は絶対値16384 DIP以内、線幅は0より大きく256 DIP以下。筆圧0〜1、傾き−90〜90度 |
| 出力処理 | 1回の書き出し全体で200万描画コマンド、512 MiB。ZIPのヘッダー再書き込みもバイト予算へ算入 |

制限を超えるデータはエラーにし、切り捨てて保存しない。失敗時は既存の保存先を保持する。
以前は開けた大きなノートでも、これらの制限を超える場合は拒否される。
通常のペン入力には筆点ごとの検証やディスク操作を追加せず、読み込み・保存・書き出しのワーカーで検証する。

## 検証

- rustfmtとClippyの全ターゲット検証。警告をエラーとして扱う。
- 32件のテスト。設定・保存・複数ページ・削除・拡大縮小・ISFの属性・PDF／PNG／SVGと、追加の攻撃用入力を検証。
- ZIPのヘッダーや内容の256か所を変異させ、パニックしないことを確認。
- ハードリンク、一時ファイルへの既存ファイル配置、保存先ロック、書き込み中の例外、出力予算超過のテスト。
- 0.10.0で生成した合成ノートを固定フィクスチャーとして読み込み、用紙・ページ順・筆跡の座標を確認。
- 配布用実行ファイルでも合成ノートを開き、数値が範囲外の別ノートを拒否した後、元の3ページ・表示中の筆跡・操作可能状態を保持することを画面で確認。
- 4種類の用紙×縦横と空白の9ページPDFを独立したパーサーで読み、画像へ描画して確認。
- PEのARM64、ASLR、DEP、CFG、Dependent Load Flag 0x800を確認。共有VC++／UCRTランタイムは不要。

Windowsの制限付きプロセスではハードリンク作成が拒否されたため、リンクを含む最終テストはサンドボックス外の通常ユーザー権限で実行した。
対象はプロジェクトのtarget内に作った検証用ファイルだけで、管理者権限は使っていない。

## 残る制約・公開後の運用

Windows InkのISF解析そのものはOS実装で、アプリと同じプロセス内で、復元後の数値検証より前に動作する。
入力バイト数は制限しているが、OS側の未修正バグ、解析中の全メモリー量・時間まで保証するものではない。
完全な隔離が必要な配布先では、ISF復元を別プロセスとJob Objectへ移す設計を追加検討する。
Win32／GDI+境界にはunsafeが残る。APIのABI・所有期間を確認したが、形式的なメモリー安全性の証明や長時間のネイティブコーデックファジングは行っていない。

実行ファイルは未署名。Authenticode署名や配布元の本人性確認は別工程である。
ノートの暗号化・自動バックアップは今回追加していない。
公開時はOS更新、依存監査、同じ回帰テストを再実行する。
依存監査が通信失敗した場合は「問題なし」とみなさず失敗終了する。

```powershell
cargo fmt -- --check
cargo clippy --locked --release --target aarch64-pc-windows-msvc --all-targets -- -D warnings
cargo test --locked --release --target aarch64-pc-windows-msvc
python scripts/check-dependencies.py
```

依存監査にはPython 3.11以降とネット接続が必要。外部へ送るのは公開依存crateの名前とバージョンだけで、ソースやノートは送信しない。

ビルド設定の根拠は[RustのCFG設定](https://doc.rust-lang.org/rustc/codegen-options/index.html#control-flow-guard)、
[MicrosoftのDEPENDENTLOADFLAG](https://learn.microsoft.com/en-us/cpp/build/reference/dependentloadflag?view=msvc-170)を参照。
